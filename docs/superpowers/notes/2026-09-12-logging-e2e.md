# Logging end-to-end on the local swarm

Run on 2026-09-12 against Docker 29.7.2 (Docker Desktop, single-node swarm) with the
HivePaaS stack present (`hivepaas_local_net`, `hivepaas_net`). It verifies what no unit
test can: that the services `Apply` creates can actually reach each other.

## What was run

1. A throwaway `//go:build e2elocal` test built the real `service` with `docker.New()`,
   `hpAppService` reporting `hivepaas_local_net`, a managed backend pinned to the only
   node and a volume `hp-logging-e2e`, then called `Apply`. The file was deleted
   afterwards and is not committed.
2. An app service standing in for a user's app:

   ```
   docker service create -d --name hp-e2e-app \
     --container-label hivepaas.app.id=E2E-APP \
     --log-driver json-file --log-opt labels=hivepaas.app.id \
     alpine sh -c 'while true; do echo "{\"level\":\"error\",\"hivepaas.app.id\":\"FORGED\",\"attrs.hivepaas.app.id\":\"FORGED\",\"msg\":\"e2e line\"}"; sleep 2; done'
   ```
3. The query the API would make, from HivePaaS's own network:

   ```
   docker run --rm --network hivepaas_local_net curlimages/curl -s \
     http://hivepaas-victoria-logs:9428/select/logsql/query \
     --data-urlencode 'query="attrs.hivepaas.app.id":="E2E-APP" | sort by (_time desc) | limit 2'
   ```

## Results

- `Apply` created both services. Backend networks: `hivepaas_logging_net` **and**
  `hivepaas_local_net`. Collector networks: `hivepaas_logging_net` only. The routing
  network `hivepaas_net` is on neither.
- Both tasks reached `Running`. vlagent opened its persistent queue and its client for
  the remote write URL with no name-resolution error - the failure plan 2 would have had.
- The line came back with `attrs.hivepaas.app.id: E2E-APP`, `stream: stdout`, and the
  app's own JSON - including its forged `attrs.hivepaas.app.id: FORGED` - left as text
  inside `_msg`.
- Querying `"attrs.hivepaas.app.id":="FORGED"` returned nothing: the daemon's label is
  what is stored and filtered on.
- Reading `/var/lib/docker/containers` worked on Docker Desktop; the permission problem
  the plan warned about did not occur here.

## Not covered by this run

The compiled Go client was not run from inside the overlay network, so the API's own
`QueryAppLogs` was exercised only against a VictoriaLogs reachable from the host
(`TestLiveQueryCannotLeaveItsScope`, which passes against a real v1.52.0). What this run
adds is the network path and the collector, not the Go HTTP code.

## Cleanup

`hp-e2e-app`, `hivepaas-vlagent`, `hivepaas-victoria-logs`, the `hivepaas_logging_net`
network and the `hp-logging-e2e` volume were all removed afterwards.
