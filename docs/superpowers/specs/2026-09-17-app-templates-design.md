# App Templates

Creating a database on HivePaaS today means creating an empty app and then
working through half a dozen settings screens: the image, a volume and where to
mount it, a healthcheck, memory limits, the app kind and its credentials, the
port. Every user does this for postgres, and every user gets a slightly
different postgres.

This adds **app templates**: a curated catalogue of common apps - postgres,
redis, minio and the like - that HivePaaS provisions in one step, from a form
generated by the template, with the configuration a maintainer has already got
right.

Templates live in their own repository, `hivepaas/app-templates`, and reach an
installation through the signed release info.

## Decisions

These were settled while designing and shape everything below.

| Question | Decision |
|---|---|
| What does a template produce? | Exactly one app. |
| Does the template keep a relationship with the app? | Yes. The app remembers its template; later revisions become updates the user reviews and applies (phase 2). |
| How do updates reach the app? | Never automatically. The user sees a diff and applies it (phase 2). |
| Conflicts between template changes and user edits | Per-field three-way merge against a stored base (phase 2). |
| Major version changes (postgres 17 to 18) | Not an update. A different major is a new app. |
| Where do templates come from? | Only the official repository, pinned by the signed release info - behind an interface other sources can implement later. |
| What does the user fill in? | Parameters the template declares, of a small closed set of types. |
| How is a template turned into configuration? | It renders to a `specmodel.AppDoc`, the format the spec exporter already writes. |
| Distributions (alpine, debian) | A variant dimension beside the version, each pair naming an exact image. |
| Where is the store? | A tab in the project, after Operations. |

## Phases

The design covers where this is going; the first phase builds the smallest
useful part of it, and stores enough that later phases need no migration of the
apps phase 1 created.

**Phase 1 - create an app from a template.** The repository format and its
tooling, fetching and verifying templates, the store, and provisioning a new app
from a template. The app records which template, version, variant and revision
it came from, together with the rendered base a later update will merge against.

**Phase 2 - updates.** Detecting that a newer revision changes an app, the three
way merge, the review dialog, applying to an existing app, detaching an app from
its template, and a per-app update policy.

**Phase 3 - breadth.** More of `AppDoc` (building from a repository, bind mounts,
config files, secrets, scheduled jobs), more parameter types, variant overrides,
and template sources other than the official repository.

Section 12 lists everything deferred and names the place in the code each
extension goes through.

### Marking deferred work in code

Deferred work is marked where it will land, with the repository's existing
convention, naming the phase - `phase 2`, `phase 3` or `later` - and the section
of this document:

```go
// TODO: app templates phase 2 - apply to an existing app through the 3-way
// merge. See docs/superpowers/specs/2026-09-17-app-templates-design.md §12.
```

Work that belongs to spec import rather than to templates is marked
`TODO: spec import`. `grep -rn "TODO: app templates\|TODO: spec import"` lists all
of it.

## 1. The template repository

```
app-templates/
├── README.md             authoring guide
├── categories.yaml       the category tree
├── tags.yaml             the tag vocabulary
├── templates/
│   ├── postgres.yaml     one file per app
│   └── redis.yaml
├── icons/
│   ├── postgres.svg
│   └── redis.svg
└── index.json            generated - never edited by hand
```

One file per app, deliberately. A directory or an archive per template would be
reviewable only by unpacking it; a single YAML file is reviewed in a pull
request like any other change.

### A template file

```yaml
apiVersion: hivepaas.com/v1
kind: AppTemplate

metadata:
  name: postgres
  title: PostgreSQL
  tagline: The world's most advanced open source relational database
  description: |
    PostgreSQL is a powerful, open source object-relational database system
    with over 35 years of active development.

    **Includes:** a persistent volume, a health check and generated credentials.
  categories: [databases/sql]
  tags: [sql, relational, open-source]
  aliases: [pg, psql]
  icon: icons/postgres.svg
  links:
    website: https://www.postgresql.org
    documentation: https://www.postgresql.org/docs/
    source: https://github.com/postgres/postgres
  license: PostgreSQL
  requires:
    versionCode: v000001

parameters:
  - name: dbName
    title: Database name
    type: string
    default: app
    pattern: '^[a-z_][a-z0-9_]{0,62}$'
  - name: username
    title: Username
    type: string
    default: app
  - name: password
    title: Password
    type: secret
    generate: {length: 32}
  - name: memoryLimit
    title: Memory limit
    type: size
    default: 512MB
    min: 128MB
  - name: dataVolume
    title: Data volume
    type: volume

variants:
  - {name: alpine, title: Alpine, description: Smaller image (musl), default: true}
  - {name: debian, title: Debian, description: "glibc, wider extension compatibility"}

versions:
  - name: "18"
    release: "18.1"
    images:
      alpine: postgres:18.1-alpine3.22
      debian: postgres:18.1-trixie
    override:
      app:
        deployment:
          storage:
            mounts:
              /var/lib/postgresql/data: null
              /var/lib/postgresql: {type: volume, source: "${{ params.dataVolume }}"}
  - name: "17"
    release: "17.6"
    default: true
    images:
      alpine: postgres:17.6-alpine3.22
      debian: postgres:17.6-trixie
  - name: "16"
    release: "16.10"
    deprecated: true
    images:
      alpine: postgres:16.10-alpine3.22

app:
  deployment:
    source:
      activeMethod: image
      imageSource: {image: "${{ image }}"}
    storage:
      mounts:
        /var/lib/postgresql/data: {type: volume, source: "${{ params.dataVolume }}"}
    container:
      healthcheck:
        enabled: true
        command: "pg_isready -U ${{ params.username }}"
        interval: 10s
        timeout: 5s
        retries: 5
    resources:
      limits: {memory: "${{ params.memoryLimit }}"}
  settings:
    kind:
      category: database
      engine: postgres
      version: "${{ version.name }}"
      database:
        dbName: "${{ params.dbName }}"
        username: "${{ params.username }}"
        password: "${{ params.password }}"
    envVars:
      data:
        - {k: POSTGRES_DB, v: "${HIVEPAAS_DATABASE_NAME}"}
        - {k: POSTGRES_USER, v: "${HIVEPAAS_USER}"}
        - {k: POSTGRES_PASSWORD, v: "${HIVEPAAS_PASSWORD}"}
    routing:
      port: 5432
```

The environment variables show why placeholders are `${{ }}` and not `${ }`:
`${HIVEPAAS_PASSWORD}` is HivePaaS's own environment variable reference and must
reach the app untouched. The kind settings produce it; the template only maps it
to the name the image expects.

### `metadata`

| Field | Required | Rule |
|---|---|---|
| `name` | yes | Equal to the file name without `.yaml`. The template's identity. |
| `title` | yes | |
| `tagline` | yes | At most 80 characters. The line on a card in the store. |
| `description` | yes | Markdown, rendered without raw HTML. |
| `categories` | yes | 1 to 3 entries of the form `parent/child`, each in `categories.yaml`. The first is the primary one. |
| `tags` | no | At most 8, each in `tags.yaml`. |
| `aliases` | no | Search terms that are not tags - other names users type. Never displayed. |
| `icon` | yes | A path to an svg or png of at most 256 KB. |
| `links` | no | `website`, `documentation`, `source`; https URLs. |
| `license` | no | |
| `requires.versionCode` | yes | The lowest `base.CurrentVersion` able to provision this template. |

Two classification fields exist on purpose and must not be confused.
`settings.kind.category` (`database`, `webapp`, `cache`) is technical: HivePaaS
acts on it - connection details, credentials, `HIVEPAAS_PASSWORD`.
`metadata.categories` is for browsing only and HivePaaS never acts on it.

`description` is markdown without raw HTML even though the official repository
is trusted. Other sources are coming (phase 3), and a store that renders HTML
from a template is a store with a stored XSS the day it reads one.

### `categories.yaml` and `tags.yaml`

```yaml
apiVersion: hivepaas.com/v1
kind: TemplateCategories
categories:
  - id: databases
    title: Databases
    children:
      - {id: sql, title: SQL}
      - {id: nosql, title: NoSQL}
      - {id: cache, title: Cache & Queues}
  - id: webapps
    title: Web Apps
    children:
      - {id: dev-tools, title: Developer Tools}
      - {id: productivity, title: Productivity}
```

```yaml
apiVersion: hivepaas.com/v1
kind: TemplateTags
tags:
  - {id: sql, title: SQL}
  - {id: s3-compatible, title: S3 Compatible}
  - {id: self-hosted-alternative, title: Self-hosted Alternative}
```

Categories are a two-level tree for navigation. Tags are flat attributes that
cut across it: `s3-compatible` gathers apps from several categories. Both are
closed vocabularies checked by the linter, because both are filters a user
clicks - free-form tags turn into `postgres`, `postgresql` and `PostgreSQL` as
three filters for one thing. Adding one is a line in the same pull request.

### `parameters`

Every parameter has `name`, `title`, `type`, and optionally `description`,
`default` and `optional`. The app's name and env are not parameters: the create
form always has them.

| Type | Constraints | Notes |
|---|---|---|
| `string` | `pattern`, `minLength`, `maxLength` | |
| `secret` | `minLength`, `generate: {length, charset}` | Generated when left empty. Stored encrypted. Its `default` is never sent to the dashboard. |
| `int` | `min`, `max` | |
| `size` | `min`, `max` | `unit.DataSize`, written `512MB`. |
| `bool` | | |
| `select` | `options: [{value, title}]` | |
| `volume` | | A cluster-volume setting the app may use. |

The set is closed and an unknown type refuses the whole template, so the form
the dashboard generates can always handle every parameter it is given.

`volume` exists because a mount in HivePaaS always names a cluster-volume
setting and derives the subpath from the app. A template never makes Docker
create a volume on its own.

### `versions` and `variants`

A version is a **major line** - `17` - pinned to an exact image. A later
revision of the repository moving `17.6` to `17.7` is an update for every app on
line `17` (phase 2). Moving an app from `17` to `18` is not an update at all: a
database has to convert its data to cross a major, which nothing here does.

| Field | Rule |
|---|---|
| `name` | The major line. |
| `release` | The exact version, displayed as `17 (17.6)`. Required. |
| `default` | Exactly one version has it. |
| `deprecated` | Hidden from the create form; apps on it keep receiving updates. |
| `image` or `images` | `image` when the template declares no variants; `images`, keyed by variant, when it does. Exactly one of the two. |
| `vars` | Other per-version values, referenced as `${{ version.vars.x }}`. |
| `override` | `override.app` is a partial `app` applied for this version - see below. |

A variant is a distribution of the same software. It is a dimension of its own
rather than more versions (`18`, `18-debian`, ...) or a parameter spliced into a
tag, because tags do not follow one pattern across distributions
(`18.1-alpine3.22`, `18.1-trixie`) and because a version may lack one: `16` above
has no debian image, and the form disables that pair instead of failing on it.

A template without variants writes `image:` on each version and has no variant
choice in the form.

Floating tags are refused: `latest`, and any tag missing the patch level the
image publishes. A floating tag changes what runs without any revision changing
- on a redeploy, or when swarm reschedules a task onto another node - which
defeats both reproducibility and the review of updates.

Changing an app's variant is never an update, for the same reason as a major: on
a database, musl and glibc can collate strings differently, and postgres moved
from alpine to debian over the same data directory can corrupt its indexes
without an error.

### `override`

A version's `override.app` is applied over the template's `app` as a JSON Merge
Patch (RFC 7396): maps merge recursively, `null` deletes a key, and lists replace
wholesale. It is a known standard with three rules, and it composes with the
spec format's choice to key mounts by target - the postgres 18 override above
moves the data mount by deleting one key and adding another.

The override is applied before placeholders are substituted, so an override can
use them. `app` is the only key `override` has; it is a key rather than the
override itself so that a version can later override something other than `app`
(`TODO: app templates later` - per-version parameter defaults, for one).

`TODO: app templates phase 3` - variants gain an `override` of their own, applied
after the version's: `app`, then the version override, then the variant override.

### `app`

`app` is a `specmodel.AppDoc`, the structure the spec exporter writes - so what a
template says and what an export of the resulting app says are the same
document. Phase 1 supports a subset of it:

| Block | Supported in phase 1 |
|---|---|
| `deployment.source` | `activeMethod: image`, `imageSource.image`, `command`, `workingDir` |
| `deployment.storage.mounts.<target>` | `type: volume`, `source`, `readOnly`, `volumeOptions.subpath` |
| `deployment.container.healthcheck` | all fields |
| `deployment.resources` | `limits` and `reservations`: `cpus`, `memory`, `pids` |
| `settings.kind` | all fields |
| `settings.envVars` | all fields |
| `settings.routing` | `port` |

Anything else is refused by the linter and by HivePaaS with a clear error.

A mount's `source` in a template is the id of a cluster-volume setting - the value
of a `volume` parameter. An export writes Docker's source there instead: the volume
name, or the host path once a bind volume has been rewritten into a bind mount.
Phase 1 only builds, so the difference costs nothing yet. `TODO: app templates
phase 2` - the merge has to map one onto the other before comparing mounts. The
subset covers postgres, mysql, mariadb, redis, mongodb and minio; extending it is
additive (section 6).

Environment variables are written `{k, v}` because that is how `AppDoc` stores
them. It is not pleasant to author, and it is not changed here: a template is an
`AppDoc`, and a friendlier template syntax would be a second format to keep in
step with the first.

### Strict parsing and `requires`

Templates are decoded strictly: an unknown field is an error, never ignored. An
older binary that skipped a field it did not understand would provision an app
different from the one the template describes, and nothing would say so.

`requires.versionCode` turns that error into a message. A template requiring a
newer HivePaaS is shown in the store, locked, with "Requires a newer version of
HivePaaS", instead of being missing or broken.

## 2. The index

`index.json` is generated by the tooling (section 10) and lets the store list,
filter and search every template from one small file.

```json
{
  "apiVersion": "hivepaas.com/v1",
  "kind": "TemplateIndex",
  "categories": [ ...the content of categories.yaml... ],
  "tags": [ ...the content of tags.yaml... ],
  "templates": [
    {
      "name": "postgres",
      "file": {"path": "templates/postgres.yaml", "sha256": "..."},
      "icon": {"path": "icons/postgres.svg", "sha256": "..."},
      "title": "PostgreSQL",
      "tagline": "The world's most advanced open source relational database",
      "categories": ["databases/sql"],
      "tags": ["sql", "relational", "open-source"],
      "aliases": ["pg", "psql"],
      "variants": [{"name": "alpine", "default": true}, {"name": "debian"}],
      "versions": [
        {"name": "18", "release": "18.1", "variants": ["alpine", "debian"]},
        {"name": "17", "release": "17.6", "default": true, "variants": ["alpine", "debian"]},
        {"name": "16", "release": "16.10", "deprecated": true, "variants": ["alpine"]}
      ],
      "requires": {"versionCode": "v000001"}
    }
  ]
}
```

The index carries no `description`: with hundreds of templates the index would
grow with text only the detail page shows. The detail page fetches the template.

The index does not carry its own revision either. It cannot contain the hash of
the commit it is part of; the revision comes from the pin that led to it.

## 3. Fetching and trust

### The source interface

```go
// TemplateSource is where templates come from. Everything else - the store,
// provisioning, and updates in phase 2 - reads templates through it.
type TemplateSource interface {
    ID() string
    Revision(ctx context.Context) (string, error)
    Index(ctx context.Context) (*templatemodel.Index, error)
    Template(ctx context.Context, name string) (*templatemodel.Template, error)
    Asset(ctx context.Context, path string) ([]byte, error)
}
```

Phase 1 has two implementations. `TODO: app templates phase 3` - a git repository
added by an administrator, and an uploaded file, are further implementations of
the same interface and change nothing that reads templates.

### The official source

The official source reads the templates pin from the signed release info, for
the installation's channel: `beta` when `config.IsBetaEnv()`, `stable`
otherwise. A channel without a pin offers no templates, and the store says so.

```
release info (ed25519 + ML-DSA-65 signatures)
  -> templates: {repo, commit, indexSha256}
    -> index.json at commit, sha256 == indexSha256
      -> templates/<name>.yaml at commit, sha256 as listed in the index
      -> icons/<name>.svg at commit, sha256 as listed in the index
```

Files are fetched from `https://raw.githubusercontent.com/{repo}/{commit}/{path}`.
A commit alone would not pin their content: nothing here can check a git object
id against what GitHub returns. The sha256 chain does, from the signature down,
and every file is checked against it before it is parsed.

The release info is cached for 15 minutes (`releaseInfoCacheTTL`), which bounds
how long a new templates revision takes to be seen.

### The cache

Verified files are stored on disk by content:

```
{AppPath}/cache/app-templates/sha256/<hash>
```

A file is checked against its hash again on every read, which is cheap. Content
addressing means a new revision re-fetches only the files that changed, and a
restart or an unreachable GitHub still serves every revision already fetched.
The parsed index is also kept in memory, keyed by `indexSha256`.

### Limits

| | Limit |
|---|---|
| `index.json` | 1 MB |
| a template file | 256 KB |
| an icon | 256 KB, svg or png |

A response over its limit is refused without being read to the end. Fetches have
a timeout and a bound on concurrency.

### Icons

HivePaaS serves icons itself rather than letting the dashboard load them from
GitHub: the dashboard then works wherever HivePaaS can reach GitHub or has the
file cached, and an icon is verified like every other file. Responses carry
`Content-Security-Policy: sandbox` and `X-Content-Type-Options: nosniff`, since
an SVG can carry script.

The icon route is public, addressed by template name and a piece of the icon's
sha256: `GET /app-templates/icons/postgres.3a18fec853.svg`. The name makes the URL
readable; the first ten hex characters of the hash change whenever the icon does,
which is what makes an immutable cache safe. The dashboard shows icons with
`<img>`, which cannot send the `Authorization` header this API authenticates with -
the same reason `/images/:imageID` is public. An icon is served only while the
current index lists that template with that hash and extension, so the route
exposes exactly the icons of the public templates repository and never answers an
old URL with new bytes.

### The local directory source

`HP_TEMPLATES_DIR` points HivePaaS at a checkout of `app-templates` and reads it
directly, with no signature and no hashes. It is honoured only when
`config.IsDevEnv()`; anywhere else it is ignored with a warning in the log.

It lets a template author try a template against a local HivePaaS without
committing and signing a release, and as a second implementation of
`TemplateSource` it keeps that interface honest.

## 4. Rendering

Rendering turns a template and the user's choices into an `AppDoc`.

```
template YAML
  1. strict parse
  2. schema validation         metadata, parameters, versions, variants
  3. resolve version, variant  exist; not deprecated when creating; the pair has an image
  4. resolve parameters        types, constraints, generate missing secrets
  5. apply version override    JSON Merge Patch over app
                               TODO: app templates phase 3 - variant override
  6. substitute placeholders   over the whole tree
  7. strict decode             into specmodel.AppDoc
  8. check supported blocks    through the block registry (section 6)
  -> AppDoc
```

Each step is a pure function - no database, no network - and is tested on its
own. The linter runs this same pipeline (section 10), so a template that renders
in CI renders in HivePaaS.

### Placeholders

| Placeholder | Value |
|---|---|
| `${{ params.<name> }}` | a parameter |
| `${{ version.name }}`, `${{ version.release }}` | the chosen version |
| `${{ version.vars.<name> }}` | a per-version value |
| `${{ variant.name }}` | the chosen variant; empty without variants |
| `${{ image }}` | the image of the chosen version and variant |

There are no expressions and no functions: a template stays a declaration.

A scalar that is exactly one placeholder takes the value's type -
`memory: "${{ params.memoryLimit }}"` is a size, not a string. A placeholder
inside a longer string is formatted into it. `$${{` writes a literal `${{`. A
reference to anything undefined is an error, which the linter reports for every
version and variant.

`TODO: app templates phase 3` - an `app` namespace (`app.name`, `app.key`), once a
template needs one.

### Two renders

Every provisioning renders twice.

- **For applying**, secrets are substituted with their values.
- **For the base** (section 5), secret placeholders are left as they are:
  `${{ params.password }}` stays literally in the output. The base is stored in a
  setting, and secrets belong only in the encrypted parameter values.

The base render is serialized as canonical YAML - keys sorted - so the same
input always hashes to the same `RenderedSHA256`.

## 5. What an app remembers

A new setting type, `app-template`, singleton at app scope, block name
`template`. A setting rather than a table gets versioning with migrations,
`EncryptedField`, audit and spec export for free.

```go
type AppTemplateSettings struct {
    Source   string `json:"source"`            // "official"
    Template string `json:"template"`          // "postgres"
    Title    string `json:"title"`             // "PostgreSQL", so displaying it needs no fetch
    Version  string `json:"version"`           // "17", the major line
    Variant  string `json:"variant,omitempty"` // "alpine"

    // Params are the values given at creation. Secrets are encrypted.
    Params map[string]*AppTemplateParam `json:"params"`

    // Base is what the template rendered to when last applied: the base of
    // the three-way merge in phase 2.
    Base AppTemplateBase `json:"base"`

    // TODO: app templates phase 2 - UpdatePolicy ("follow" | "pinned").
}

type AppTemplateParam struct {
    Value  string         `json:"value,omitempty"`
    Secret EncryptedField `json:"secret,omitzero"`
}

type AppTemplateBase struct {
    Revision       string    `json:"revision"`       // templates repository commit
    Release        string    `json:"release"`        // "17.6"
    TemplateSHA256 string    `json:"templateSha256"`
    Rendered       string    `json:"rendered"`       // canonical YAML of the base render
    RenderedSHA256 string    `json:"renderedSha256"`
    AppliedAt      time.Time `json:"appliedAt"`
}
```

Phase 1 writes this setting and reads it only for display. It is complete now so
that phase 2 can update apps phase 1 created, without a migration that would
have to reconstruct a base nobody recorded.

### The base is the render, not the template

Storing the template file and rendering it again when needed looks equivalent
and is not. A later HivePaaS that fixes a bug in rendering would render the old
template differently from what was actually applied, and every app would show
changes no template made. The stored render is exactly what was applied, and a
base that cannot drift.

### Secrets

The base holds secret placeholders, not secrets. In phase 2 the current state of
the app is read with secrets decrypted - internally, never through the API - and
a secret field equal to its parameter's value is replaced by the placeholder
before comparing. Equal means the user did not change it; different means they
did. Diffs show "secret changed", never a value.

### Parameters are fixed

Parameters cannot be edited after creation. Changing the memory limit or the
password is done on the app, like on any other app, and phase 2's merge treats
it as a user change. Editing parameters and re-rendering would add a third kind
of change to the merge. `TODO: app templates later`.

### Clones and previews

An app cloned from an app that has a template carries the `app-template` setting
through the existing settings clone, and stays managed. Preview apps of such an
app are child apps and follow the same path.

### Spec export

`app-template` registers a `SpecPolicy` and is exported in full, its secret
parameters following the export's secrets mode like every other encrypted field.
The spec exporter's coverage test refuses a setting type without a policy, so
this cannot be forgotten.

## 6. Provisioning

### Packages


`templatemodel` plays the role `specmodel` plays for export: the durable format,
sharing no types with DTOs. `templatemodel`, `templaterender` and `templaterepo`
are pure - no database, no network, no service - so the linter in
`tools/apptemplate` uses exactly the code HivePaaS runs.

Building an `AppDoc` into settings and a service spec lives in `specservice`,
not in the template service. It is the applying half of the spec, the mirror of
export, and the spec import will use it too (`TODO: spec import`). Which blocks
can be built is declared once, in `specmodel.CheckBuildable`, and both rendering
and the builders' registry are tested against it.

### The block registry

```go
// builders turns each supported AppDoc block into settings and service spec.
// A block with no builder is refused - never skipped - so a template can not
// silently provision less than it describes.
func (s *service) builders() map[specmodel.Block]blockBuilder {
    return map[specmodel.Block]blockBuilder{
        specmodel.BlockDeploymentSource:      s.buildSource,
        specmodel.BlockDeploymentStorage:     s.buildStorage,
        specmodel.BlockContainerHealthcheck:  s.buildHealthcheck,
        specmodel.BlockDeploymentResources:   s.buildResources,
        specmodel.BlockSettingsKind:          s.buildKind,
        specmodel.BlockSettingsEnvVars:       s.buildEnvVars,
        specmodel.BlockSettingsRouting:       s.buildRouting,
        // TODO: app templates phase 3 - more blocks.
    }
}
```

Extending what templates can do is registering a builder, and the round-trip
test (section 11) holds it to what export produces.

### `appprovisionservice`

```go
// ProvisionApp creates an app, its swarm service and its settings. A request
// with no settings is plain app creation.
ProvisionApp(ctx context.Context, db database.IDB, req *ProvisionAppReq) (*ProvisionAppResp, error)
```

It is a service of its own rather than more of `appservice`: it assembles an app
with its whole configuration, of which an empty app is only the smallest case.

### Refactors this needs

A usecase cannot call another usecase, so two pieces move down to services,
unchanged in behaviour and covered by the tests their usecases already have:

1. **The core of `appuc.CreateApp`** - key, uniqueness, network, the initial
   service spec, default settings - moves into `appprovisionservice.ProvisionApp`.
   `appuc.CreateApp` calls it with an empty configuration.
2. **Building mounts**, from `appsettingsuc/storage_settings_update.go` - volume
   lookup, subpath, the bind-mount rewrite, permissions, the pin conflict check -
   moves into `volumeservice`, behind a request type of its own, since a service
   cannot take `appsettingsdto.Mount`. `UpdateAppStorageSettings` converts and
   calls it.

Creating a deployment needs no move: `appdeploymentservice.CreateDeploymentAndTask`
already exists and `DeployApp` uses it.

### Creating an app from a template

```
POST /projects/:projectID/:projectEnv/apps/from-template
{
  "name": "main-db",
  "template": "postgres",
  "version": "17",
  "variant": "alpine",
  "params": {"dbName": "app", "memoryLimit": "1GB", "dataVolume": "01J..."}
}
```

Parameter values are JSON values of the parameter's type; a size is a string such
as `"1GB"`.

1. **Authorize** as creating an app: `GetAuthInEnv(ActionTypeWrite, false)`.
2. **Load** the template from the source. Check `requires`, the version and
   variant, and the parameters; a `volume` must exist and be usable from the app's
   scope.
3. **Render** twice (section 4).
4. **In one transaction:**
   - `appprovisionservice` creates the app and its service spec, with the
     placeholder image `CreateApp` uses today;
   - `specservice` builds the settings (`app-deployment`, `app-kind`, `env-var`,
     `app-routing`) and the mounts, healthcheck and resources of the spec;
   - the `app-template` setting is added;
   - the swarm service is created and everything persisted;
   - environment variables and routing are applied, as `appcloneservice` does
     after persisting a clone;
   - a deployment is created;
   - `app-create` is audited with `template`, `version`, `variant`, `release` and
     `revision` in its detail.
5. **After the transaction**, the deployment task is dispatched: it pulls the real
   image and updates the service, as any deployment does.
6. **Respond** `{appId, deploymentId}`.

A failure inside the transaction removes the swarm service already created, as
`CreateApp` does today, so no running service is left without a record. A failed
deployment afterwards leaves the app in place with a failed deployment, like any
other app.

## 9. Security

- **What runs is decided by the signature.** A template chooses images. Every
  template reaches an installation through the signed release info and the
  sha256 chain beneath it, and nothing reads a template before it has been
  verified.
- **Only the official source in production.** The local directory source is
  refused outside development.
- **Secrets.** Secret parameters are generated server-side, stored only as
  `EncryptedField`s, never returned as defaults, never written into the base, and
  never shown in a diff.
- **Untrusted text.** Descriptions render without raw HTML; icons are served
  sandboxed; every file has a size limit.
- **Parameters are validated server-side** against the template's schema: the
  form the dashboard generates is a convenience, not a check.
- **References are scoped.** A `volume` parameter must name a volume the app's
  scope can use, checked exactly as the storage settings screen checks it.

## 10. Tooling, CI and publishing

### `tools/apptemplate`

In the hivepaas repository, and built on `apptemplateservice`'s own rendering, so
the linter and HivePaaS cannot disagree about a template.

```
go run ./tools/apptemplate lint   <dir>
go run ./tools/apptemplate index  <dir> [--check]
go run ./tools/apptemplate render <dir> <template> --version 17 [--variant alpine] [--param k=v]...
go run ./tools/apptemplate pin    <dir>
```

- `render` prints the `AppDoc`, for authors checking what a template produces.
- `pin` prints `{"repo", "commit", "indexSha256"}` for the checkout's `HEAD`, to be
  pasted into `release.json`.

### What `lint` checks

- **Schema:** strict parse; `metadata.name` equals the file name; `apiVersion` and
  `kind`.
- **Metadata:** `tagline` present and at most 80 characters; `description`
  present; `categories` 1 to 3 and in `categories.yaml`; `tags` in `tags.yaml`;
  `links` are https URLs.
- **Icon:** exists, svg or png, at most 256 KB.
- **Versions and variants:** each version has `release`; exactly one `default`;
  images are exact tags; `image` or `images`, not both; every variant referenced
  is declared.
- **Parameters:** a known type; valid constraints; `default` satisfies them.
- **Rendering:** every version and variant renders with default parameters -
  dummy secrets, a dummy volume id - with every placeholder resolved and only
  supported blocks used.
- **Index:** `index.json` equals what `index` would write.

### CI in `app-templates`

```yaml
- uses: actions/checkout@v4
- uses: actions/checkout@v4
  with:
    repository: hivepaas/hivepaas
    ref: <pinned tag or sha>
    path: hivepaas
- run: |
    cd hivepaas
    go run ./tools/apptemplate lint ..
    go run ./tools/apptemplate index --check ..
```

The hivepaas ref is pinned, not `main`, so templates are checked by the parser of
the binary that will read them. It moves when hivepaas gains a block or a
parameter type.

### Publishing

1. A pull request to `app-templates`; CI lints; merge to `main`.
2. `go run ./tools/apptemplate pin <dir>` on the merged commit.
3. Put the pin into `release.json` under `beta`, `make release-sign`, commit to
   the `release` branch.
4. Check it on a beta installation, then copy the pin to `stable` and sign again.

Templates reach installations without a HivePaaS release, but never without the
offline signature. That is deliberate: a template decides which images run on a
user's machine.

## 11. Testing

- **Rendering:** table-driven tests for each pipeline step, with template files
  under `testdata`: strict parsing, merge patch (including `null` deletes and list
  replacement), placeholder typing and escaping, undefined references, every
  parameter type and constraint, secret generation, version and variant
  resolution, the base render keeping secret placeholders, canonical hashing.
- **Sources:** the official source against an in-memory HTTP server - a file whose
  hash does not match the index, an index whose hash does not match the pin, size
  limits, the disk cache serving an unreachable server, a corrupted cache entry
  refetched. The local directory source refused outside development.
- **Build round trip:** render an `AppDoc`, build it into settings and a service
  spec, and pass those through the exporter's own mapping functions: the result
  must equal the rendered `AppDoc` for every supported block except storage, whose
  `source` means something different on each side (section 1, `app`). Export and
  build cannot drift apart without this failing.
- **Refactors:** the existing tests of `UpdateAppStorageSettings` move with the
  functions they test and pass unchanged; `ProvisionApp` gains tests of its own,
  since `CreateApp` has none.
- **Usecase:** creating from a template with a fake source; an invalid parameter,
  an unknown version or variant, a missing volume, and a template requiring a
  newer HivePaaS each refused before anything is written; the audit entry carries
  the template detail and no secret.
- **Spec export:** the coverage oracle includes `app-template`; an exported app
  created from a template carries its binding with secrets per mode.
- **Tooling:** `lint` against valid and broken fixture repositories; `index
  --check` detecting a stale index.
